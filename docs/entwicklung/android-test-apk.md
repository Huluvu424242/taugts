# Android-Test-APK vom aktuellen master

Story [#230](https://github.com/Huluvu424242/taugts/issues/230) ergänzt den ausschließlich manuell startbaren Workflow **Android Test-APK** unter `.github/workflows/android-test-apk.yml`. Er ist **kein offizielles Release**: Es werden weder Tag noch GitHub Release, Commit, Versionsänderung im Repository oder automatische Verteilung erzeugt.

## Test-APK erzeugen

1. Der Workflow muss durch einen separaten PR geprüft, in `master` gemergt und vor seiner ersten Ausführung nach `agent-rules/05-security-tooling.md` ausdrücklich freigegeben sein.
2. GitHub öffnen: **Actions → Android Test-APK → Run workflow**. Als Workflow-Branch `master` wählen. Der Job checkt unabhängig von der Auswahl ausdrücklich den aktuellen `master` aus und prüft dessen Commit-SHA.
3. Als `build_number` eine **positive ganze Zahl größer als die in `pubspec.yaml` eingetragene Buildnummer und größer als die auf dem Testgerät installierte Buildnummer** angeben. Die Buildnummer darf höchstens `2100000000` betragen. Die Test-APK verwendet die unveränderte `versionName` aus `pubspec.yaml` sowie diese temporär übergebene Android-`versionCode`. Beispiel: Bei `version: 0.1.0+8` kann `build_number: 9` verwendet werden, solange auf dem Gerät eine niedrigere Buildnummer installiert ist. Eine wiederholte Testinstallation erfordert gegebenenfalls jeweils eine höhere Buildnummer.
4. Den Lauf öffnen. Der **Job Summary** protokolliert den verwendeten `master`-Commit, die Quellversion und den Test-`versionCode`. Analyse, Flutter-Tests, Build und Signaturprüfung müssen erfolgreich sein.
5. Unten auf der Run-Seite unter **Artifacts** die Datei `taugts-test-<kurz-SHA>-build<Nummer>` herunterladen. GitHub liefert ein ZIP mit APK, Prüfsummendatei und `build-info.txt`. Das ZIP entpacken. Der Download ist **fünf Tage** verfügbar.

Unter Windows kann die Prüfsumme mit `Get-FileHash .\taugts-test-....apk -Algorithm SHA256` mit dem Wert aus der zugehörigen `.sha256`-Datei verglichen werden.

## Auf Android installieren und Migration prüfen

1. **Vor dem Update die Daten über die Exportfunktion der bestehenden App sichern** und die Sicherung getrennt vom Gerät verwahren. Ein Update kann bei fehlerhafter Migration oder beschädigten Daten nicht einfach durch Deinstallation rückgängig gemacht werden.
2. Zunächst die **bisherige, mit dem offiziellen Release-Keystore signierte Version** mit einem echten Bestand installieren bzw. verwenden. Mindestens ein Erlebnis, ein Produkt und eine Bewertung eignen sich zur Sichtprüfung.
3. Die neue APK auf das Gerät übertragen und öffnen; falls Android nachfragt, die Installation aus dieser Quelle ausdrücklich erlauben. **Nicht vorher deinstallieren und keine App-Daten löschen**, sonst ist es kein Migrationstest.
4. Android akzeptiert ein In-Place-Update nur bei übereinstimmender Application-ID (`de.huluvu.taugts`), kompatibler Signierung und zulässiger (in der Regel höherer) Buildnummer. Der Test-Workflow verwendet die **bestehenden Release-Secrets** und damit denselben Keystore wie der offizielle Release-Workflow. Sind diese Secrets anders belegt, ist Update-Kompatibilität nicht gewährleistet.
5. App starten und prüfen, ob die alten Daten, Verknüpfungen, Bewertungen und Historien vollständig erhalten sind; kontrollieren, ob neue Funktionen funktionieren. Bei einem Schemawechsel zusätzlich die tatsächlich erforderliche Migration prüfen. Ein grüner GitHub-Workflow beweist **nicht**, dass eine reale Datenbankmigration erfolgreich war.
6. Ergebnis mit Ausgangsversion, ursprünglichem Datenbankschema, Test-Buildnummer, Commit-SHA und beobachtetem Datenbestand festhalten. Bei einem Fehler vorhandene Daten nicht durch wiederholtes Installieren oder Löschen gefährden.

Ein Android-Downgrade auf eine geringere Buildnummer wird normalerweise verweigert. Auch eine frühere APK mit höherer Buildnummer kann eine neuere Datenbank oft nicht lesen. Darum nach einem Test nicht einfach eine ältere Version darüber installieren. Für einen Rollback nur einen zuvor gesicherten, kompatiblen Datenbestand auf einem geeigneten Installationsstand wiederherstellen.

**Wichtige Altversionen:** Bei der Konsolidierung der Entwicklungsmigrationen wurde das Schema auf eine neue Baseline gestellt. Nicht jeder historische Vorab-Datenbankstand besitzt einen unterstützten Upgradepfad. Ein erfolgreicher APK-Updatevorgang garantiert daher keine Migrationsfähigkeit einer beliebigen alten Datenbank.

## Sicherheit, Werkzeuge und Betriebsregeln

- **Akteure und Zweck:** Der Repository-Verantwortliche startet den Workflow ausschließlich manuell über `workflow_dispatch`, um eine Testversion von `master` auf realen Android-Geräten zu prüfen. Es gibt keinen Push-, PR- oder Zeitplan-Trigger. Eine erste oder nicht ausdrücklich freigegebene Ausführung bleibt verboten.
- **Berechtigungen:** Ausschließlich `contents: read`. Keine GitHub-Schreibberechtigung, keine Tags, Commits, Releases oder Deployment-Berechtigungen. Der Checkout verwendet keine persistenten Git-Credentials.
- **Inputs und Datenfluss:** Eingabe ist eine numerische Buildnummer. Der Runner liest den aktuellen öffentlichen Repositoryinhalt und reguläre Flutter-/Android-Abhängigkeiten sowie die vier **bereits vorhandenen GitHub-Secrets** `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. Die APK erhält die produktive Signatur. Keines dieser Geheimnisse darf geloggt, in den PR oder ins Artefakt übernommen werden.
- **Bedrohungsanalyse:** Wer einen signierten APK-Build über GitHub Actions starten oder Artefakte herunterladen kann, erhält eine technisch vertrauenswürdige, mit der produktiven App updatekompatible Binärdatei. Bei einem öffentlichen Repository können Artefakte je nach GitHub-Zugriffsregeln auch von Dritten heruntergeladen und außerhalb des Projekts verbreitet werden. Deshalb ausschließlich vertrauenswürdige `master`-Commits verarbeiten, Artefakte nicht als offiziellen Download bewerben und die Berechtigung zur Workflow-Ausführung einschränken bzw. überwachen. Eine kompromittierte Build-Action könnte Geheimnisse lesen; Pinning reduziert Versionsdrift, beseitigt jedoch nicht jedes Supply-Chain-Risiko.
- **Signierung:** Wie beim vorhandenen Release-Workflow wird der Keystore nur auf dem flüchtigen Runner aus dem Secret rekonstruiert; fehlende Secrets führen zum Abbruch. Die Signatur wird mit `apksigner verify` kontrolliert. Der Schlüssel wird im abschließenden `always()`-Schritt entfernt; ein Fehler oder Runner-Ausfall kann dessen Ausführung verhindern, weshalb GitHub-hosted ephemere Runner Voraussetzung sind.
- **Abhängigkeiten / Herkunft:** Der Workflow verwendet dieselben per Commit-SHA gepinnten `actions/checkout@v6`, `actions/setup-java@v5` und `subosito/flutter-action@v2` wie der vorhandene Release-Workflow; zusätzlich die per Commit-SHA gepinnte offizielle `actions/upload-artifact@v4`. Vor der Freigabe Versionen, Wartung, bekannte Sicherheitsmeldungen, Rechte und Lizenzen der Actions erneut prüfen. Flutter `stable` und abhängige Android-Toolchains können sich zwischen Läufen ändern; die genaue Version ist dem Run-Log zu entnehmen.
- **Outputs und Aufbewahrung:** Nur das fünf Tage vorgehaltene ZIP mit APK, SHA-256 und `build-info.txt` sowie GitHub-Run-Logs und Summary. Für die Logs gilt die im Repository konfigurierte GitHub-Actions-Log-Aufbewahrung (nicht die Fünf-Tage-Regel des Artefakts). Es werden keine Benutzer- oder Datenbankinhalte hochgeladen.
- **Laufzeit/Kosten:** Ein Ubuntu-Runner führt Abhängigkeitsinstallation, Analyse, Tests und Release-Build aus, mit `timeout-minutes: 45`. Der Ressourcenverbrauch wird nach dem für das Repository gültigen GitHub-Actions-Preismodell berechnet; jeder manuelle Lauf kostet zusätzliche Runner-Minuten und Artefaktspeicher.
- **Nachvollziehbarkeit:** Run-Auslöser, Zeitpunkt, Commit-SHA, Version, Buildnummer, Laufstatus und Artefaktname bleiben im GitHub-Run sichtbar. APK und Prüfsumme lassen sich zusammen prüfen.
- **Deaktivierung/Rollback:** Ohne neue Runs entstehen keine neuen APKs. Workflow-Deaktivierung oder Entfernung erfolgen nur nach den GitHub-/AGENTS-Freigaberegeln. Bei Verdacht auf Signierschlüsseloffenlegung: Secrets widerrufen/rotieren und die Updatefähigkeit bestehender Apps prüfen. Das Löschen eines Workflows oder Artefakts macht bereits verteilte APKs nicht rückgängig.

Die vorhandene offizielle Release-Erstellung unter `android-release.yml` wird nicht geändert.
